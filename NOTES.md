Single-file GST billing, production and inventory web app for a commutator manufacturer.
Use this file as the briefing before changing anything.

## 2. Working pattern the user expects

1. Edit `commutator-mfg.html`.
2. Preview it (artifact or screenshot) and **wait for the user to say "apply" or "push"**. Do not push on your own, except when the user reports something broken and asks for the fix.
3. Rebuild the Firebase file: `python3 build_fb.py` → `commutator-mfg-firebase.html`.
4. Run the mock harness `python3 fb_test.py` (must print `failed 0`).
5. Copy the built file to the repo as `index.html`, commit, push to `origin main`.
6. Tell the user it takes a minute or two for GitHub Pages; hard refresh (Ctrl+F5) if stale.

Commit messages end with the attribution trailers from the session reminder.
The live site is not reachable from the sandbox (proxy 403), so test the built file locally with Playwright.

`tools/build_fb.py` builds `index.html` from `src/commutator-mfg.html` (paths inside the script point at /mnt/user-data/outputs; adjust if that folder is gone). `tools/fb_test.py` is the mock test harness. Keep these three in sync with the live `index.html`.

## 3. Domain rules (do not break)

- **Persons** use `BILL-` numbers, no GST, cash or GPay. **Firms (companies)** use `INV-` numbers, GST 18%, bank only.
- GST: CGST 9% + SGST 9% within the state, IGST 18% interstate (place of supply on the invoice).
- Stock is derived, never stored: opening + purchases + production − sales − production use ± returns/rejects (`stock(b, i)` around line 480).
- Payments are rows in `b.tx` (bank id, `cash` or `gpay`). Cash and GPay are built-in accounts with openings `b.cashOpen`, `b.gpayOpen`.
- Returns: sales return → credit note `CN-`, purchase return → debit note, rejects reduce stock.
- Invoices carry an LR number (transport) shown on the invoice and ledger.
- Reports are computed live from the arrays; there are no stored totals.
- "Cash & GPay people" (bottom of Expenses) is only a **view** over existing cash/GPay transactions plus pins (`b.pp`). It is not a new transaction type. Do not add one.

## 4. Data model

State `S = { biz: [...], cur }`. Each business `b` has arrays:

`items, inv, banks, tx, pur, prod, cust, sup, exp, sr, prr, rej, pp` plus `cashOpen, gpayOpen`, `name`.

- New arrays must be added in four places: `fixBiz` (default `b.x = b.x || []`), `mk` (new business), `MKS`, `SH_ARR` (shared-sync list), and `shBuild` default. Missing one breaks old data or sync.
- `fixBiz(b)` runs on load and migrates old shapes; keep it additive.
- Item types: `raw`, `fg` (finished goods), by-products/scrap. Finished goods have a BOM (`eff(b, i)`).
- Firestore: collection `rec` holds the synced state (via `shApply` / `shBuild`).

## 6. Firebase layer (added by `build_fb.py`)

- Login overlay `#login` (opaque from first paint, "Loading…" card, hidden by `shInit` for non-Firebase paths) with an animated SVG background `.lgbg` (SMIL `animateTransform`, 90/60/36 s rings, soft CSS glow).
- `FB.config` holds the public web config; `FB.owners` lists emails allowed to reset all data (currently empty → nobody).
- First user signs in with email and password; others need to be on the Firestore allowlist, otherwise "No access".
- `window.__fbSdk` can be mocked, which is what `fb_test.py` does.
- Info tooltips: `INF(text)` helper; `#tip` has `z-index:120` so it shows above the login overlay.
- Custom domain / username rename are GitHub settings, not code (renaming the repo or username changes the URL; Firebase "Authorized domains" must be updated to match).

## 7. Task playbooks

### Add a field or feature to a screen
1. Change the `vXxx` renderer and its `doXxx` handler.
2. If new data: add the array/field in the four places in §4.
3. Escape every user string with `esc()` before putting it in HTML (units, HSN, names, notes). One XSS-style bug was found and fixed here before.
4. Check desktop (1280) and mobile (390) widths and dark/light.
5. Preview → wait for "apply" → build, test, push (§2).

### Change a calculation (GST, stock, profit)
1. Edit the shared helper (`tot`, `stock`, `calc`), not each screen.
2. Re-run the guide data scenario (§9) and confirm the figures still match.
3. Check balance sheet balances and trial balance totals agree.

### Add a report or a nav tab
1. Add to `NAVS` and a `vXxx(b)` function; reports go in the `vRep` tab list.
2. Add its icon to `IC` if it is a tab.
3. Make sure PDF/print styles still work (`.paper` is white on purpose for printing).

### Fix a layout bug
- Check both the in-page table (`#lst`, ledger statement) and the modal (`#ov .card:has(.paper)`).
- Particulars columns need `white-space:normal; overflow-wrap:anywhere` so Credit/Balance never clip.
- Global rule `prefers-reduced-motion` turns off all animation; anything that must always move (the header logo ring) needs its own `!important` exception.

### Change the login screen
- Edit the HTML/CSS strings inside `build_fb.py` (not the source file). Keep the card opaque on first paint to avoid the app flashing before the login appears.

### Deploy
- See §2. After pushing, wait for Pages, then hard refresh.

### Make documentation or screenshots
- Drive the real UI with Playwright (Chromium), seed with the test data in §9, take element screenshots with dark colour scheme (`color_scheme='dark'`).
- The printable statement is white by design; for dark guides inject CSS only for the screenshot.

## 8. Testing

- Playwright + Chromium only. `fb_test.py` (mock Firebase, about 100 checks incl. sign-in states), `scratch.py` (data flow), exploratory `hunt.py`, `xss.py`.
- Always test the built `index.html`, not only the source, because most bugs came from the Firebase layer.
- Reduced-motion check: `browser.new_context(reduced_motion='reduce')`.

## 10. Known gotchas

- Do not add a separate transaction type for Cash/GPay people (user rejected it).
- The animated login background must stay subtle and slow (user asked twice).
- Tooltips and overlays: keep `#tip` above `#login`.
- Unescaped user text in `innerHTML` is the main bug class.
- Scratchpad files vanish between sessions; commit anything that must last into the repo.
